`C:\Users\jotac\OneDrive\Documents\DEV\jota_integrador` — projeto iniciado em 2026-09-06. Plataforma SaaS que centraliza informações fiscais de empresas conectando-se às APIs oficiais do governo (Integra Contador/SERPRO), com dois produtos sobre a mesma base: **JOTA FISCAL** (visão do empresário) e **JOTA CONTÁBIL** (visão do contador, gestão de carteira de empresas).

Hierarquia de 3 níveis (não é multi-tenant simples de 1 nível): Dev/Admin Jota → Contador (tenant) → Empresa Cliente (sub-tenant do contador). Todo dado de domínio precisa validar posse nos dois níveis em cascata — maior risco de BOLA/IDOR do que os projetos anteriores do ecossistema.

Stack: React + Vite (frontend), NestJS (backend), PostgreSQL via Supabase, Redis, Docker — mesma stack prática do [[project_deliveryhub]], apesar do `ADR-001-STACK-OFICIAL.md` do vault ainda registrar Vue/Nuxt como oficial (desatualizado, não corrigido ainda).

O dado mais crítico do sistema é o **certificado digital (A1/A3)** de cada empresa — usado para assinar digitalmente perante o Fisco. Exige cofre dedicado + criptografia AES-256 em repouso + isolamento por empresa + auditoria de todo uso + controle de expiração/rotação — tratado como chave privada de produção, nunca como upload comum.

Plano de produto original (brainstorm que originou o projeto): `may_memory/28-JotaIntegradorFiscal/primeiroPlano.md`. Fases planejadas: 1) Fundação (login, cadastro, certificado, créditos, dashboard) → 2) Fiscal (NF-e/NFC-e/NFS-e/XML) → 3) Receita/Simples Nacional → 4) Caixa Postal → 5) Inteligência fiscal (alertas automáticos, anomalias).

## Modelo real de certificado/SERPRO confirmado com a doc oficial (2026-09-06) — mudou premissa original

Consultando `apicenter.estaleiro.serpro.gov.br/documentacao/api-integra-contador` (quick start + api reference + cenários trial), o modelo assumido em `primeiroPlano.md` (certificado por empresa cliente) **estava errado**. O real:

- Autenticação usa `Role-Type: TERCEIROS` + **certificado digital único da Jota** (e-CNPJ, o mesmo da contratação do produto) — não um certificado por empresa. `POST https://autenticacao.sapi.serpro.gov.br/authenticate` com Basic auth (consumer key/secret) retorna **dois tokens** (`access_token` + `jwt_token`, ~33min); toda chamada ao gateway exige os dois headers juntos (`Authorization: Bearer` + `jwt_token:`), sem endpoint de refresh — só reautenticar no 401.
- Acesso por empresa-cliente é controlado por **procuração eletrônica** (outorgada pela empresa à Jota via e-CAC/gov.br), não por certificado que a empresa entrega. SERPRO expõe serviço `PROCURACOES` pra consultar status programaticamente.
- Isso inverteu o formato do risco do certificado: em vez de N certificados isolados (1 por empresa, blast radius pequeno), há **1 certificado cujo comprometimento afeta todos os clientes simultaneamente** — vira o single point of failure mais crítico da plataforma.
- Payload de toda chamada de negócio: `{contratante, autorPedidoDados, contribuinte, pedidoDados: {idSistema, idServico, versaoSistema, dados}}` — `contribuinte` é a empresa cliente (nosso `empresa_id` resolvido pra CNPJ).
- **Existe ambiente trial oficial** (não confundir com a tela "Ateste de Serviço" do portal cliente, que é uma etapa de homologação pra liberar produção, coisa diferente e que não bloqueava o usuário — "nenhum ateste pendente"): `https://gateway.apiserpro.serpro.gov.br/integra-contador-trial/v1/`, CNPJ fixo `00000000000000`, só `Authorization: Bearer <token de demonstração público>` (sem certificado, sem `jwt_token`), com cenário documentado por serviço em `.../cenarios_trial/cenarios_<nome>/`. ## Módulo de créditos implementado (2026-09-06) — commit `726f003`, atomicidade real via função Postgres

**Decisão técnica central:** débito/crédito de saldo NUNCA pode ser um `UPDATE` + `INSERT` separados via client JS (não é atômico — se o segundo falhar, sobra saldo alterado sem auditoria). Migration `0011_funcoes_creditos.sql` criou `debitar_creditos()`/`creditar_creditos()` como funções Postgres `SECURITY DEFINER` com `SELECT ... FOR UPDATE` (lock de linha) + a constraint `saldo_atual >= 0` que já existia desde a migration 0004 — tudo numa transação só, chamado via `.rpc()` do Supabase client. **Testado isoladamente por SQL puro antes de escrever qualquer código NestJS** (padrão que vale repetir: validar a lógica de banco pura primeiro, só depois construir a camada de aplicação em cima).

`creditos_movimentos.empresa_id` virou **nullable** (era `not null` desde a migration 0004) — ajustes manuais de saldo (recarga de plano, correção administrativa) não têm empresa associada, só débitos por consumo real têm.

**Desvio de convenção deliberado:** `CreditosModule` exporta `DebitarCreditosUseCase`/`EstornarCreditosUseCase` (casos de uso concretos), não só o token do repositório — diferente do padrão que critiquei/segui nos módulos anteriores ("nunca exportar caso de uso, só porta"). Justificativa: esses casos de uso carregam a regra de negócio de **custo por operação** (`dominio/credito.ts`, catálogo `CUSTO_POR_OPERACAO` do plano original do produto) — se `serpro/` usasse só `CREDITOS_REPOSITORIO` diretamente, teria que importar e conhecer o catálogo de custo também, duplicando lógica entre módulos. Quando o caso de uso encapsula uma regra de negócio real (não é só um wrapper fino sobre o repositório, como era `ObterEmpresaUseCase`), exportá-lo é a escolha certa.

**Integração real com `serpro/`:** `ConsultarCcmeiUseCase` agora debita crédito **antes** de chamar o SERPRO (falha rápido sem gastar cota da API se não há saldo) e **estorna** (padrão saga/compensação, já que não existe transação distribuída real entre nosso banco e o SERPRO) se a chamada falhar depois — fecha o TODO que tinha ficado documentado no módulo SERPRO ("creditosConsumidos: 0 -- módulo de créditos ainda não existe").

**Tratamento de erro:** `SaldoInsuficienteError` é uma exceção de **domínio** (não conhece HTTP, Clean Architecture) — criei `SaldoInsuficienteFilter` (`@Catch` global, registrado em `main.ts`) que converte pra `HTTP 402 Payment Required` com mensagem clara, em vez de cada caso de uso que gasta crédito ter que fazer esse mapeamento na mão. Padrão a reaproveitar pra outras exceções de domínio que forem aparecendo (ex: futura exceção de "procuração inválida" já é tratada como `ForbiddenException` direto no caso de uso, não precisou de filtro — só criar filtro quando a exceção de domínio precisa cruzar múltiplos módulos/casos de uso).

**Erro cometido e corrigido durante a escrita (não chegou a rodar assim):** tentei importar `PaymentRequiredException` de `@nestjs/common` — não existe nesse pacote (confirmado pelo compilador). Corrigido construindo a resposta HTTP manualmente no filtro (`response.status(402).json(...)`) em vez de uma classe de exceção pronta.

**Validado de ponta a ponta com API real + chamada real ao SERPRO:** saldo inicial 0 → contador não pode se autocreditar (403, RBAC) → `SUPER_ADMIN`/`ADMIN_FINANCEIRO` credita 5 → cada consulta CCMEI real (SERPRO trial) debita 1 crédito automaticamente, confirmado saldo caindo 5→4→3→2→1→0 e `consultas_serpro.creditos_consumidos` batendo exatamente com `creditos_movimentos` — sem consultar sem saldo retorna `402` com mensagem "Saldo insuficiente: disponível 0, necessário 1", não um 500 genérico.

## Módulo de Caixa Postal implementado (2026-09-09) — commit `e3a8e35`, fecha o item #5

Formato exato de payload/response veio de **chamadas reais contra o ambiente trial** (`gateway.apiserpro.serpro.gov.br/integra-contador-trial/v1/Consultar`, mesmo token público de sempre) — mais confiável que a doc quando ela está fora do ar.

**Padrão do módulo:** `SincronizarMensagensUseCase` busca uma página por vez (sem paginação automática — cada chamada custa crédito, paginar sozinho multiplicaria custo sem o contador saber) e faz upsert idempotente por `(empresa_id, serpro_isn)` — nunca sobrescreve mensagem já existente, preservando status de leitura marcado localmente. `ObterDetalheMensagemUseCase` é lazy+cacheado: só chama o SERPRO (e debita crédito) na primeira leitura de cada mensagem; depois disso vem do Storage de graça. `corpoModelo` (corpo da mensagem) vem do SERPRO com placeholders `++1++`, `++2++`... substituídos por `variaveis[]` — sem essa substituição o texto fica ilegível, confirmado testando.

**Cofre sem cifragem, de propósito:** diferente do cofre de certificados, o conteúdo de mensagem do Caixa Postal NÃO é cifrado — classificação LGPD "Restrito" (`docs/SEGURANCA.md §5`), não "Crítico" como certificado. Bucket privado (sem policy pra `authenticated`/`anon`) já é a proteção adequada pra esse nível.

**Três bugs reais achados testando de ponta a ponta** (não só lendo código) — os dois primeiros na camada COMPARTILHADA do SERPRO, afetam qualquer módulo futuro que use esse gateway, não só caixa_postal:

1. **`SerproGatewayHttp` só checava HTTP status, não o status de negócio embutido.** O SERPRO embrulha erro (payload inválido, etc) dentro de HTTP 200 com um campo `status` interno diferente de 200 — CCMEI nunca expôs isso porque seu cenário trial sempre retorna sucesso; CAIXAPOSTAL expôs na primeira tentativa com payload errado. Corrigido: `SerproGatewayHttp` agora também checa `corpo.status` (aceita number ou string — o SERPRO usa os dois formatos dependendo do serviço), só então marca `sucesso: true`. **How to apply:** qualquer novo módulo SERPRO deve assumir que HTTP 200 sozinho não garante sucesso — esse fix já cobre isso automaticamente pra quem usa `SerproGatewayHttp`, mas vale lembrar ao debugar um "sucesso" que não devia ser.

2. **Cenários de demonstração trial do SERPRO são inconsistentes ENTRE SI sobre qual CNPJ fixo aceitam.** `MSGCONTRIBUINTE61` só aceita `99999999999999`; `MSGDETALHAMENTO62` e `CCMEI` só aceitam `00000000000000` — o outro valor dá "Dados inválidos" pros dois lados (confirmado testando as 4 combinações). `montarEnvelope()` (`dominio/serpro.ts`) ganhou parâmetro `documentoTrial` opcional por chamada (default `00000000000000`, preserva CCMEI) — só produção que ignora completamente esse parâmetro. **How to apply:** ao integrar um serviço SERPRO novo, se o trial devolver "Dados inválidos" mesmo com o payload certo, testar os dois CNPJs fixos (`00000000000000` e `99999999999999`) antes de assumir que o payload está errado — pode ser só o cenário de demonstração sendo específico sobre qual espera.

3. **Bug dormente desde a sessão de assinaturas, não relacionado a SERPRO:** a migration `20260909000002` (módulo assinaturas, mesma sessão) fez `CREATE OR REPLACE FUNCTION creditar_creditos` acrescentando um parâmetro com `DEFAULT`, esperando substituir a função original de 3 parâmetros — mas Postgres só substitui função com a MESMA assinatura; parâmetro novo cria uma **sobrecarga** ao lado da antiga, não substitui. Toda chamada com só 3 argumentos (usada por `EstornarCreditosUseCase` e pelo crédito manual do admin) ficou **ambígua** entre as duas sobrecargas e falhava com `"Could not choose the best candidate function"`. Só apareceu agora porque foi a primeira vez que `EstornarCreditosUseCase` rodou depois daquela migration (o fluxo de estorno do caixa_postal). Corrigido com `DROP FUNCTION` explícito da sobrecarga de 3 parâmetros (`migration 20260909000004`) — só a versão de 4 parâmetros com `DEFAULT` sobrevive. **How to apply:** ao adicionar parâmetro a uma função Postgres existente via `CREATE OR REPLACE`, mesmo com `DEFAULT`, sempre `DROP FUNCTION` explícito da assinatura antiga na mesma migration (ou confirmar que só uma sobrecarga existe depois) — `CREATE OR REPLACE` nunca remove uma assinatura antiga sozinho. Vale conferir se esse mesmo padrão foi usado em outro lugar do schema sem esse cuidado.

**Validado ponta a ponta com API real + chamadas reais ao SERPRO trial (não mock):** sincronização trouxe 50 mensagens reais do cenário de demonstração, campos mapeados corretos, idempotência (re-sync não duplica), isolamento cross-tenant, detalhe de mensagem com HTML final legível (placeholders substituídos), cache de conteúdo (segunda leitura não gera nova chamada nem novo débito), marcar como lida, e confirmação de que os dois fixes do gateway SERPRO não quebraram CCMEI (testado nos dois lados depois de cada mudança).

## Módulo contábil (Plano de Contas + Lançamentos) implementado (2026-09-09) — commits `d618c3f` (backend) + `e42493a` (frontend), primeiro módulo minerado do jotaCaixa

**Achado central que mudou o design:** o `lancamentos` do jotaCaixa é uma tabela de linhas soltas (1 conta + `tipo: Entrada|Saida` + valor por linha, correlacionadas só por um campo texto `documento`) — sem nada no banco garantindo que as linhas de um mesmo lançamento fechem (débito=crédito). Isso bate com o incidente documentado lá (`INSTRUCOES_RESTAURACAO.md`: lançamentos perdidos/corrompidos, balanço não fechava). Decisão de design pra não repetir: escrita só através de `criar_lancamento_contabil()` (função Postgres `SECURITY DEFINER`, migration `20260909000005`), que recebe a partida inteira (jsonb) e valida numa transação só — débito=crédito, mínimo 2 partidas, toda conta existe/é da mesma empresa/está ativa/é analítica — antes de gravar cabeçalho (`lancamentos_contabeis`) + linhas (`lancamentos_partidas`). RLS bloqueia INSERT direto em ambas as tabelas pra `authenticated` (`with check (false)`) -- a função é a única porta de escrita, mesmo princípio já usado em `debitar_creditos`/`creditar_creditos`.

**Nunca UPDATE/DELETE em lançamento** -- corrigir é sempre `estornar_lancamento_contabil()`, que cria um lançamento novo com débito/crédito invertidos e marca o original como `estornado=true` (rastro contábil completo preservado, nunca "como se não tivesse acontecido"). Estornar um lançamento já estornado é bloqueado.

**Saldo nunca cacheado** -- `saldo_conta_contabil(conta_id, ate_data)` soma `lancamentos_partidas` na hora, toda vez. jotaCaixa tinha uma tabela `saldo_contas` separada (provável segunda causa do balanço não fechar, cache podendo divergir da soma real) -- decisão deliberada de não repetir isso; se performance virar problema real com volume alto, materializar depois (YAGNI), não preventivamente.

**Plano de contas** minerado do `FormPlanoContas.tsx` do jotaCaixa: código hierárquico, `sintetica` (agrupadora, não recebe lançamento) vs analítica, `grupo` (ativo/passivo/patrimônio líquido/receita/custo/despesa) determinando natureza de saldo -- mas ao contrário do jotaCaixa (que guardava `saldo_tipo` como campo editável derivado só por convenção de UI), aqui `naturezaDoGrupo()` é uma função pura no domínio, nunca persistida -- não pode divergir do grupo por erro de digitação/edição manual. Flags de propósito especial (`conta_caixa_banco`, `conta_a_receber`, `conta_a_pagar`) consolidadas de 5 flags booleanas sobrepostas do jotaCaixa (`is_caixa`, `is_banco`, `is_conta_caixa_banco`, etc.) pra 3 -- extensível quando o módulo de conciliação (#11) precisar de mais granularidade, não antes.

**Escrita (criar conta, criar/estornar lançamento) é só contador dono ou plataforma** -- nunca a própria empresa-cliente (é trabalho de escritório contábil), mesmo critério de `exigirPosseDeContador` já usado em bloqueio de empresa/contador. ## Mapeamento construído (só frontend) (2026-09-11/12)

Usuário escolheu `/mapeamento` como próximo item após Extrato Manual + picklists. Ao minerar `jotaCaixa/src/{pages/Mapeamento.tsx, hooks/useMapeamento.ts}`, descobri que o **backend do jota_integrador já tinha antecipado esse módulo** -- o docstring de `ListarPendentesUseCase` (`conciliacao-bancaria/aplicacao/casos-de-uso/listar-pendentes.usecase.ts`) já dizia "equivalente a Mapeamento.tsx do jotaCaixa" desde que foi escrito. Toda a API necessária já existia: `GET /pendentes` (cross-conta, exatamente o que a aba "Extratos Não Mapeados" precisa), `GET /lancamentos` (`ListarConciliadasUseCase`, nunca consumido por nenhum frontend antes), e `GET /contas-a-pagar`/`GET /contas-a-receber` (parcelas em aberto, já com `parcelas[]` aninhado). **Zero mudança de backend nesta tarefa.**

**Diferença deliberada do jotaCaixa:** lá, o "extrato mapeado" e "extrato pago" são estados independentes (`mapearExtrato` só atualiza `mapeado_parcela_id`, não mexe em `data_pagamento` da parcela) -- por isso o jotaCaixa tinha uma 4ª aba de "parcelas não mapeadas" genuinamente distinta de "parcelas não pagas". No jota_integrador, `VincularTransacaoParcelaUseCase` já dispara `RegistrarPagamentoUseCase`/`RegistrarRecebimentoUseCase` na hora de vincular (decisão tomada na sessão da Conciliação Bancária, ver seção acima) -- **vincular É pagar**, não existe estado intermediário. Por isso as abas "CP em Aberto"/"CR em Aberto" aqui são simplesmente as parcelas com `status !== 'paga'`, calculadas no frontend via flatten de `listarContasPagar`/`listarContasReceber` (sem filtro de "já tentou conciliar ou não" -- não existe esse conceito aqui). Mesma razão: **não existe endpoint de "desmapear"/desfazer conciliação** -- desfazer exigiria estornar o lançamento contábil gerado, que é um fluxo próprio (já existe pra CP/CR via `estornar-pagamento`/`estornar-recebimento`, mas não foi estendido pra esse caso nesta tarefa, ficou fora de escopo deliberadamente).

**Arquivos novos (`jota_fiscal_frontend`):** `pages/Mapeamento.tsx` (4 abas: Não Conciliadas reaproveitando `PainelTransacoesPendentes` que já existia; Conciliadas nova `TabelaTransacoesConciliadas.tsx` só-leitura; CP/CR em Aberto nova `TabelaParcelasEmAberto.tsx` genérica parametrizada por `rotuloParte`, clicar na linha abre `DetalheContaPagarDialog`/`DetalheContaReceberDialog` -- **os mesmos diálogos já usados em `ContasAPagar.tsx`/`ContasAReceber.tsx`**, sem duplicar lógica de registrar pagamento/recebimento). `servicos/conciliacaoBancaria.js` ganhou `listarLancamentosConciliados` (só faltava o wrapper, a rota já existia).
