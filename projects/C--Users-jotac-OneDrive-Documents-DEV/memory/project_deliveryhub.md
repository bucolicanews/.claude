## Gotcha: Supabase local key naming (2026-08-12)

The Supabase CLI's `npx supabase status` (run from `deliveryhub_white_label/`, where `supabase/config.toml` lives) prints both legacy JWT-style keys (`ANON_KEY`, `SERVICE_ROLE_KEY`) and newer prefixed keys (`PUBLISHABLE_KEY` = `sb_publishable_...`, `SECRET_KEY` = `sb_secret_...`). `serer_delivery/.env`'s `SUPABASE_SERVICE_ROLE_KEY` had the `sb_publishable_...` value pasted into it by mistake, which made the seed script (`scripts/seed-primeiro-boot.ts`, using the Supabase Admin API to create users) fail with `AuthApiError: User not allowed (403 not_admin)` — the publishable/anon key has no admin rights.

**Why:** the two key-naming schemes look similar and it's easy to grab the wrong one when copy-pasting from `supabase status` output.
**How to apply:** if `seed:primeiro-boot` or any Admin API call fails with `403 not_admin`, check that `SUPABASE_SERVICE_ROLE_KEY` in `serer_delivery/.env` is the secret/service_role key (`sb_secret_...` or the `service_role`-role JWT), not the publishable/anon one. Also note: Supabase local services must be started from `deliveryhub_white_label/` (that's where `supabase/config.toml` lives), not from `serer_delivery/`.

## Two independent backend checkouts, same local DB

`deliveryhub_white_label/server_delivery` (git submodule) and the standalone `serer_delivery/` repo are **separate git checkouts** of the same remote (`jmoka/serer_delivery.git`) — each has its own `node_modules` and `.env`, so a fix in one (e.g. `.env` keys, `npm install`) does not propagate to the other and must be repeated in both. **How to apply:** when doing setup/install/env fixes for this project, apply them to both `deliveryhub_white_label/server_delivery` and `serer_delivery/` unless told only one is in use. User gave this as a standing order (2026-08-13, reaffirmed after a doc commit landed in the submodule but not the standalone checkout): after any commit/push that touches `server_delivery` content, always check the standalone `serer_delivery/` checkout too and `git pull origin main` there to keep both in sync — do this proactively, without being asked each time.

**Two concrete ways this bit during the 2026-08-15 security audit — both worth avoiding next time:**
1. Added `helmet`/`@nestjs/throttler` (backend) via `npm install` in `serer_delivery/`, then just ran `npm install --package-lock-only` in the submodule to sync the lockfile — that only rewrites `package-lock.json`, it does **not** populate `node_modules`. Submodule's `npm run start` failed with `Cannot find module 'helmet'` until a real `npm install` (no flag) was run there too. **How to apply:** after adding a dependency in one checkout, run a real `npm install` (not `--package-lock-only`) in the other one too — check `ls node_modules/<pkg>` if unsure it actually landed.

Symptom was CORS errors in the browser (`No 'Access-Control-Allow-Origin' header`) that looked like a code bug but was actually a missing env var in the checkout actually being run. **How to apply:** whenever adding a *new* required env var (not just editing a value), add it to `.env` in both `serer_delivery/` and `deliveryhub_white_label/server_delivery/` — grep both for the var name to confirm before declaring a fix done.

## Regra de negócio: carrinho/venda só existe no plano delivery (2026-08-13)

Se a loja do cliente não tem o plano "delivery" contratado, a loja não tem carrinho de compras nem venda — funciona só como vitrine (catálogo de produtos pra visualização, sem checkout). O fluxo de carrinho/pedido só é habilitado quando o plano do restaurante é do tipo delivery.

Se o plano for só "salão" (dine-in, sem delivery), a loja também vira vitrine apenas (sem carrinho/venda pelo site) e, além disso, **não aparece listada no DeliveryHub** (marketplace/busca principal) — só lojas com plano delivery aparecem lá.

**Why:** regra de negócio do produto — diferencia planos de vitrine (só exibição) dos planos delivery (venda completa + listagem no marketplace). Plano só-salão é pra restaurante que atende só presencialmente, então não faz sentido aparecer pra quem busca delivery.
**How to apply:** ao mexer em carrinho, checkout, ou qualquer fluxo de venda, verificar o tipo/plano do restaurante primeiro — não assumir que carrinho está sempre disponível. Ao mexer na listagem/busca do DeliveryHub (home, busca de restaurantes), filtrar por plano delivery. Ao investigar bugs de "carrinho sumiu", "não consigo comprar" ou "loja não aparece na busca", checar o plano antes de assumir defeito.

### Regressão do próprio fix (2026-08-16): esqueci de testar o boot antes de mandar fazer deploy

O commit `d78df7b` acima (`imports: [CommonModule]` só no `AuthModule`) passou no `tsc --noEmit` e no `nest build`, mas **quebrou o boot em produção** — 502 + CORS bloqueado em TODAS as rotas depois do deploy no EasyPanel, não só as protegidas por `RestaurantOwnerGuard`. Causa: `RestaurantOwnerGuard` é usado via `@UseGuards()` em vários módulos além do `AuthModule` (ex. `AgenteImpressaoModule`, e todo módulo que usa a rota de restaurante) — importar `CommonModule` só no `AuthModule` não propaga a dependência pros outros. Nest falhava com `UnknownDependenciesException` já no `NestFactory.create()`, então o processo nunca chegava a escutar a porta — só descobri rodando `node dist/src/main.js` local e vendo o app não printar "Nest application successfully started". Corrigido marcando `CommonModule` como `@Global()` (commit `a6436b2`, mesmo padrão do `SupabaseModule`, que já é `@Global()` por exatamente esse motivo).

**Why:** `tsc`/`nest build` só checam tipo, não checam se o grafo de DI do NestJS resolve em runtime — um guard usado em `@UseGuards()` fora do módulo onde foi declarado só enxerga as dependências desse módulo se elas vierem de um módulo `@Global()` (como já é `SupabaseModule`) ou se TODO módulo consumidor importar o módulo da dependência nova.
**How to apply:** antes de mandar fazer deploy de qualquer mudança que adiciona uma dependência nova a um **guard, interceptor ou pipe compartilhado** (não um service comum de um módulo isolado), rodar localmente `npm run build && node dist/src/main.js` (ou `npm run start:dev`) e conferir que aparece `"Nest application successfully started"` sem `UnknownDependenciesException` antes — não confiar só no `tsc --noEmit`. Se a dependência nova vem de um módulo próprio (não `@Global()` ainda) e é usada por guard/interceptor espalhado pelo app, o caminho mais simples costuma ser marcar esse módulo como `@Global()` em vez de importar em cada consumidor.

Commits do fix da regressão: `a6436b2` (`serer_delivery` e submódulo) + `eacede5` (`deliveryhub_white_label`, ponteiro). **Usuário confirmou em produção (2026-08-16, fim do dia) que o cadastro de restaurante + pagamento de fatura via Pix voltou a funcionar** depois desse segundo deploy — bug e regressão ambos fechados, nenhum follow-up pendente.

## Gotcha: `fetch failed` / `SocketError: other side closed (UND_ERR_SOCKET)` do backend pro Supabase local (2026-09-04)

Erro intermitente nos logs do NestJS: `TypeError: fetch failed` causado por `SocketError: other side closed (UND_ERR_SOCKET)`. Não é bug de código nem do Supabase em si — é o proxy de portas do Docker Desktop (Windows/WSL2) derrubando em silêncio uma conexão keep-alive ociosa entre o Node (fetch nativo via `undici`) e o Kong local (porta 54331); o Node tenta reaproveitar o socket morto e a chamada falha pontualmente. Confirmado reproduzindo em duas instâncias diferentes do backend (reiniciar sozinho não resolve, é ambiente, não estado do processo).

**Corrigido:** `SupabaseService` (`serer_delivery` + submódulo) ganhou um `fetch` customizado passado via `createClient(url, key, { global: { fetch: fetchComRetry } })` — detecta esse erro específico (`err.cause?.code === 'UND_ERR_SOCKET'` ou mensagem contendo "other side closed") e tenta de novo uma vez com socket novo, transparente pro resto do código. Outros erros continuam subindo normal.

**Why:** sintoma reaparece cada vez que uma conexão fica ociosa por um tempo e o Docker Desktop a derruba sem avisar — comportamento do ambiente Windows/WSL2, não do app.
**How to apply:** se esse erro voltar a aparecer nos logs (procurar por `UND_ERR_SOCKET` ou "other side closed"), o retry já deve estar absorvendo a maioria dos casos silenciosamente — só investigar mais a fundo se o erro aparecer duas vezes seguidas pro mesmo request (aí não é mais o socket morto, é outra coisa).

### Gotcha de deploy: duas branches "iguais" em checkouts diferentes do mesmo remote geram hashes diferentes (2026-08-21)

Ao commitar a mesma mudança de backend nos dois checkouts (`serer_delivery` e `deliveryhub_white_label/server_delivery`, sempre nessa ordem/duplicunderplicado durante a sessão) numa branch de feature, e depois fazer merge de cada um pra `main` + push **separadamente**, o primeiro push (`serer_delivery`) definiu o hash canônico no remote; o segundo push (submódulo) foi rejeitado (`fetch first`) porque seu merge local gerou um commit com **conteúdo idêntico mas hash diferente** (fast-forward de uma branch de feature commitada independentemente). Resolvido com `git diff origin/main main --stat` (confirmou zero diferença de conteúdo) + `git reset --hard origin/main` no submódulo — descartando o commit local redundante sem perder nada. Depois disso, o ponteiro do submódulo no frontend (que apontava pro hash antigo/descartado) precisou de um commit extra pra apontar pro hash real publicado.
**How to apply:** ao mesclar uma branch de feature que existe nos dois checkouts do backend pra `main`, mesclar e dar push em **um** primeiro, depois no outro rodar `git fetch && git diff origin/main main --stat` antes de tentar push — se vazio, `git reset --hard origin/main` em vez de tentar empurrar um commit duplicado. Só então atualizar o ponteiro do submódulo no frontend.

**Cuidado (2026-08-23):** `git reset --hard origin/main` descarta qualquer alteração NÃO commitada nesse checkout também, não só o commit duplicado — bati nisso de verdade: o submódulo tinha um arquivo com WIP não commitado (feature de opacidade em Aparência, sem relação com o que eu estava fechando) e o reset apagou. Só não perdeu nada porque o mesmo arquivo tinha a mesma alteração intacta no outro checkout (`serer_delivery`), então deu pra restaurar copiando. **Antes de rodar `reset --hard` nesse fluxo, sempre `git status --short` primeiro e, se houver algo não commitado sem relação com o commit duplicado, copiar/backup pra fora do repo (ou pro outro checkout, se também existir lá) antes do reset.**

## Feature: integração GDOOR SLIM via agente local `api_gdoor` (2026-08-26/27) — em produção

Terceiro "agente local" do projeto (depois de impressão e — futuramente — outros), no mesmo padrão do `print-agent`: `deliveryhub_white_label/api_gdoor` (Python/FastAPI, não Node) roda na máquina do restaurante onde o **GDOOR SLIM** (PDV/fiscal via Firebird) está instalado, e faz *polling* no `server_delivery` em vez de esperar ser chamado — necessário porque o backend roda na nuvem e não alcança uma máquina atrás de NAT doméstico.

- **Pareamento:** token gerado em `/restaurante/config` (painel, componente `GdoorAgentePanel`) colado numa janela Tkinter (`parear_gui.py`, aberta por `parear.bat`) que também mostra se o GDOOR foi detectado e qual CNPJ tem cadastrado (lido de `EMITENTE.CNPJ` — não existe campo "SERIAL" dedicado no GDOOR, CNPJ foi adotado como identificador da instalação, autorizado pelo usuário). Backend confere esse CNPJ contra um `gdoor_cnpj_esperado` cadastrado pelo dono — pareamento só é íntegro se os dois baterem (`gdoor.service.ts`, `jobsPendentes` bloqueia se não confere).
- **Fluxo de pedido → pré-venda:** pedido vira `delivered` → `PedidosService` só faz `INSERT` numa fila (`gdoor_jobs`, com `product_id → codigo_gdoor` já resolvido pelo backend antes de enfileirar) → agente puxa via `GET /agente-gdoor/jobs/pendentes` a cada `POLLER_INTERVALO_SEG` (padrão 5s) → grava `VENDAS`/`ITEVENDAS` no Firebird (`MODELO='PV'`, mecanismo descoberto por engenharia reversa do GDOOR.exe, documentado em `api_gdoor/INTEGRACAO.md` — **não** `PDV_CLIENTE`, ver correção abaixo) → reporta `POST .../concluido` ou `/erro`.
- **Mapeamento de produto → código GDOOR:** feito pelo **dono no painel** (nova seção "Mapeamento de produtos GDOOR" em `/restaurante/config`), não editando nada na máquina do restaurante — o agente reporta o catálogo `ESTOQUE` a cada ~1min (`gdoor_estoque_cache`), o dono escolhe o código por produto (`gdoor_produto_mapeamento`), e o backend já resolve isso no payload do job — o agente nunca decide mapeamento sozinho.
- **Sem `.env` em produção:** mesmo padrão do `print-agent/config.py` — URL de produção fixa no código (`local_config.DEFAULT_BACKEND_URL`), token e dados locais do Firebird gravados em `local_config.json` (`%APPDATA%\DeliveryHubAgenteGdoor`), porque uma instalação distribuída pra máquina de um restaurante não tem como receber um `.env` editado na mão. `.env` continua existindo só como atalho de dev nesta máquina (tem prioridade se presente). `public/api_gdoor.rar` é o pacote baixável (ainda não é `.exe` único via PyInstaller como o print-agent — roda via `.bat` + venv Python 32-bit, que precisa estar instalado na máquina).

**Gotcha real desta sessão:** ao mesclar a branch de feature pra `main` nos dois checkouts do backend, bati de novo no gotcha já documentado acima (hash diferente por checkout) — dessa vez resolvido só com `git fetch && git pull origin main` no segundo checkout (fast-forward limpo, sem precisar de `reset --hard`) porque nenhum dos dois tinha commit local extra além do que já tinha sido publicado pelo primeiro.

**Why:** replica intencionalmente o padrão do agente de impressão (usuário pediu explicitamente "da mesma forma que implantamos o print-agent"), incluindo a decisão de configuração sem `.env` — só percebida depois que o usuário questionou como isso funcionaria numa instalação real, sem acesso pra editar arquivo na máquina do cliente.
**How to apply:** se pedirem pra estender a integração GDOOR (novo campo na pré-venda, outro tipo de documento fiscal, etc.), o padrão de fila (`gdoor_jobs`) + polling + resolução de mapeamento no backend antes de enfileirar deve ser mantido — não adicionar lógica de decisão no agente Python, ele só executa o que o job já vem resolvido. Se pedirem pra empacotar como `.exe` (like print-agent), unificar poller + GUI num processo só primeiro (hoje são dois: `iniciar.bat` roda uvicorn+poller, `parear.bat` roda só a GUI) — ver `print-agent/gui.py` como referência de como fazem isso num processo Tkinter só.

### Sincronização de clientes GDOOR + fix do "Concluir" na pré-venda (2026-08-27/28) — em produção

Duas frentes na mesma sessão longa:

1. **Sincronização de clientes GDOOR ↔ DeliveryHub**, espelhando a de produtos: modal bidirecional (`GdoorClientesPanel`), tabelas `gdoor_cliente_cache`/`gdoor_cliente_mapeamento`/`gdoor_criar_cliente_jobs`. **Regra de negócio explícita do usuário, testada em duas direções antes de fechar:** só sincroniza cliente/GDOOR que tenha CPF/CNPJ — telefone sozinho **não** é critério de match (pedido inicial era incluir telefone como fallback, revertido pelo próprio usuário: "só sincroniza se tiver cpf ou cnpj sem isso não sincroniza"). Também dá pra disparar pré-venda pelo fechamento de comanda/mesa do Salão (dine-in), não só delivery — reaproveita a mesma fila `gdoor_jobs`.
2. **"Concluir"/"Alterar" não funcionava numa pré-venda criada pelo sistema** (a tela simplesmente voltava, sem erro nenhum) mesmo com `VENDAS`/`ITEVENDAS` batendo campo a campo com uma pré-venda nativa. A causa raiz, achada por último: `PDV_ARQBIN` (`ID_VENDA, OBJETO`) guarda um **dump em texto puro do objeto de venda inteiro** (`Objeto.Campo=valor`, `\r\n`, ~190 linhas — cabeçalho + itens + pagamento default + tributos com casas cheias) que a tela do GDOOR usa pra **recarregar a pré-venda ao abrir**, não lê mais as tabelas SQL nesse ponto. Sem essa linha, a tela não erra — só não acha nada pra processar. Reconstruído campo a campo (formato, ordem e nomes confirmados byte a byte contra pré-vendas 100% nativas) em `firebird_client._gerar_blob_pdv_arqbin()`, chamado dentro de `criar_pre_venda()`. Documentado por completo em `api_gdoor/INTEGRACAO.md`.

**Erros que custaram tempo real nessa investigação (vale não repetir):**
- Uma tabela chamada `PREVENDA`/`PREVENDA_ITENS` parecia óbvia pelo nome, mas é legada/staging, não relacionada — dois registros de teste gravados lá nunca apareceram na tela do GDOOR. Só descartada depois que o usuário confirmou manualmente que não apareciam.
- `MOV_OPERADORES` foi inserido na criação por analogia (parecia fazer parte do padrão de tabelas vinculadas por `ID_VENDA`), mas na verdade só existe em vendas **já concluídas** — é o próprio GDOOR que cria essa linha ao clicar "Concluir". Inseri-la cedo demais era exatamente o que fazia a tela "tentar processar e voltar" sem terminar — regressão sutil, difícil de perceber porque não dava erro.

**O que finalmente funcionou, na ordem que importou:** comparar campo a campo contra registros nativos reais (o usuário criando uma pré-venda pela própria tela e me dando o número) sempre rendeu mais que engenharia reversa por nome de coluna. O passo decisivo foi tirar um **snapshot de contagem de linhas de TODAS as ~500 tabelas do Firebird** antes/depois do usuário criar uma pré-venda nativa — revelou `PDV_ARQBIN` (tabela que a busca por convenção de nome `ID_VENDA`/`ID_VENDAS` não teria pego sozinha, já que o padrão de busca anterior era só grep de coluna).

**Why:** documentar isso evita repetir os mesmos dois becos sem saída (`PREVENDA`, `MOV_OPERADORES` prematuro) numa sessão futura, e registra a técnica que finalmente funcionou.
**How to apply:** se aparecer de novo um sintoma "grava/lista certo mas uma ação da tela do GDOOR não funciona e não dá erro", suspeitar primeiro de um blob `PDV_ARQBIN` desatualizado/ausente antes de qualquer outra coisa — e se for uma tabela/mecanismo GDOOR totalmente novo (não coberto por `INTEGRACAO.md`), preferir o snapshot de contagem de tabelas (antes/depois de uma ação nativa real) a adivinhar por nome de coluna.

## Fix: exclusão de garçom apagava a conferência em cascata (2026-08-31) — em produção

**Incidente real relatado pelo usuário:** operador excluiu garçom(ns) e as conferências (fechamentos de turno) desses garçons sumiram junto, sem aviso nenhum.

**Causa raiz:** `GarconsService.remover()` (`src/salao/garcons.service.ts`) fazia `DELETE FROM garcons` direto. Três tabelas têm FK `ON DELETE CASCADE` em `garcom_id`: `garcom_turnos` (a conferência em si — campo `resumo` congela vendas/gorjeta/comissão no fechamento do turno), `garcom_comissoes_lancamentos`, `garcom_repasses` (repasse já pago). `orders.garcom_id` é `SET NULL` (a comanda sobrevive, só perde o vínculo). Excluir o garçom apagava as três em cascata, silenciosamente.

**Fix:** `remover()` agora conta (`count: 'exact', head: true`, em paralelo) linhas em `garcom_turnos`/`garcom_comissoes_lancamentos`/`garcom_repasses`/`orders` pro `garcom_id` antes de deletar — se qualquer uma tiver histórico, recusa com `400 BadRequestException` orientando a "desativar" em vez de excluir. Mesmo padrão já usado em `MotoboyService.excluirPeloRestaurante` (bloqueia exclusão se tem `motoboy_comissoes`). O mecanismo de "desativar" (`garcons.ativo`) já existia pronto (toggle no frontend), só a exclusão que não respeitava isso. Frontend (`restaurante-garcons/index.jsx`): `remover()` não tinha `try/catch` — erro do backend passava em silêncio; adicionado tratamento + exibição da mensagem.

**Decisão consciente de escopo, documentada no plano:** não mudei as FKs de CASCADE pra SET NULL nem criei coluna de snapshot de nome (padrão que existe pra `orders.cliente_mesa_nome`) — isso teria que lidar com RLS de `garcom_comissoes_lancamentos` (não tem `restaurant_id` próprio, só chega no restaurante via join com `garcons`; `garcom_id` nulo quebraria a policy). O bloqueio de exclusão sozinho já fecha o buraco por completo daqui pra frente (exclusão com histórico nunca mais acontece, logo o cascade nunca mais dispara). Se quiser essa camada extra de proteção (defesa em profundidade contra outros caminhos de exclusão), fica como frente separada.

**Dado já perdido no incidente que gerou esse fix não tem como voltar por código** — só recuperação via backup/point-in-time restore do Supabase, se existir um de antes da exclusão (não fiz isso, é operação no painel do Supabase).

**Why:** perda de dado de auditoria/financeiro (conferência de turno = vendas+gorjeta+comissão apuradas) é o tipo de problema que pede o padrão mais conservador possível: bloquear em vez de tentar recuperar/reconstruir depois.
**How to apply:** se aparecer o mesmo tipo de pedido pra outra entidade que tem FK CASCADE ligada a dado financeiro/auditoria (ex.: excluir uma regra de comissão, um caixa, etc.), replicar esse padrão de "contar histórico relacionado antes do delete, bloquear com 400 se houver" — é mais simples e seguro que mexer em ON DELETE de FK existente.

### Gotcha grave: loop `for f in ...; do cp "$f" ".../$f"; done` falha silenciosamente no Git Bash desse Windows (2026-09-01)

Ao sincronizar vários arquivos de backend de uma vez pro submódulo com um loop bash (`for f in caminho1 caminho2; do cp "$f" "C:\...\destino\$f"; diff "$f" "C:\...\destino\$f" && echo OK; done`), o `cp` silenciosamente não escreveu no destino real (path com backslash misturado com `$f` de forward-slash confunde o MSYS) — mas o `diff` seguinte reportou "OK" mesmo assim (aparentemente por comparar algo diferente do que eu esperava, não o arquivo real). Resultado: o submódulo ficou **dias** desatualizado (mtime parado em 28/08) sem eu perceber, incluindo uma feature inteira (split_ativo/comissão) que eu já tinha "confirmado" sincronizada antes. Só descobri ao rodar `git status`/`git diff --stat` no submódulo antes do commit e ver zero mudanças onde eu esperava várias. O sintoma colateral: o loop também deixava pra trás um arquivo lixo tipo `server_delivery$f` ou `server_delivery${f}` solto na raiz do repo frontend (efeito colateral do path mal resolvido).

**Why:** a interpolação de `$f` (valor com `/`) dentro de uma string com backslashes Windows, dentro de um loop `for`, não é confiável nesse ambiente — não é um problema do padrão de sync em si (que já funcionou muitas vezes com comandos individuais), é especificamente a combinação loop+interpolação+path misto.
**How to apply:** nunca usar loop `for` com `$f` interpolado dentro de um path Windows pra sincronizar múltiplos arquivos — copiar **um arquivo por vez**, com o caminho completo escrito por extenso (não interpolado), e depois de TODOS os `cp`, rodar `ls -la` nos destinos pra conferir o `mtime` de hoje antes de confiar no `diff`. Se o `git status` do submódulo depois de "sincronizar" aparecer vazio quando eu esperava mudanças, é sinal de que o sync não aconteceu de verdade — não assumir que "sem diff" = "sincronizado", checar mtime primeiro.

## Bug real corrigido (2026-09-05): preço promocional ignorado ao cobrar produto — delivery E salão

Usuário reportou: produto custa R$40, em promoção por R$35 (campo `preco_promo`, mesmo padrão de exibição usado em Salão/Balcão/catálogo: `preco_promo ?? price`) — comanda do Salão cobrava o preço cheio. Investigado e confirmado que o **mesmo bug existia no delivery também** (usuário suspeitava que fosse só Salão).

**Causa raiz:** todo ponto que grava `order_items.unit_price` a partir de `products.price` direto — `pedidos.service.ts criar()` (delivery), `salao.service.ts incluirItens()` (comanda do dono), `salao-pdv.service.ts incluirItens()` (PDV/balcão — balcão reusa esse mesmo caminho), `auto-atendimento.service.ts adicionarItens()` (comanda do cliente via QR na mesa) — todos faziam `.select('id, price, is_active')` sem `preco_promo`, e usavam `prodMap[id].price` direto. Achado com `grep` no projeto inteiro por `unit_price:.*\.price` — só 6 ocorrências, uma delas (`combos.service.ts`) é preço de item dentro de combo (`preco_no_combo`, lógica separada e correta).

**Bônus encontrado na mesma varredura:** `salao-pdv.service.ts` (impressão de conferência ao fechar comanda) re-buscava `products.price` fresco pro recibo em vez de usar o `order_items.unit_price` já gravado — corrigido pra usar o valor já salvo (evita divergência se o preço do produto mudar depois do pedido).

**Fix:** os 4 pontos de inserção passaram a fazer `.select('id, price, preco_promo, is_active')` + `prodMap[id].preco_promo ?? prodMap[id].price`. Testado local: comanda de mesa com X-Burguer (R$25,90, promo R$10) fechou com `unit_price:10`/total R$10; pedido delivery do mesmo produto também saiu com total R$10 (confirma que afetava os dois canais).

**Why:** `preco_promo` só é considerado na hora de **exibir** o preço (frontend/catálogo), nunca foi propagado pro cálculo que efetivamente grava o valor cobrado no banco — bug estrutural desde que o campo existe, não uma regressão recente.
**How to apply:** se aparecer um 5º lugar que insere `order_items` a partir de `products.price` (ex. um novo canal de venda), replicar o mesmo padrão `preco_promo ?? price`. Se aparecer "recibo/conferência mostra valor diferente do cobrado", suspeitar de re-fetch de `products.price` em vez de usar o `unit_price` já persistido — mesma classe do bug encontrado na impressão do PDV.

## Bug real corrigido (2026-09-08): pagamento online (Stripe/PagBank) pulava confirmação do estabelecimento e ia direto pra "Em Preparo"

## Feature: tela de acompanhamento de vendas Stripe (estabelecimento + admin) + repasse automático (2026-09-08) — código em produção, falta 1 passo manual do usuário

Pedido do usuário: ver valor exato que a loja recebe por venda Stripe (tarifa, comissão, saldo) e marcar "repasse feito" quando a Stripe efetivamente paga a loja — automático via `payout.paid`, não manual.

**Dados capturados no `payment_intent.succeeded`** (`stripe.service.ts processarPaymentIntent`): busca o charge com `balance_transaction` expandido pra pegar `fee` (tarifa Stripe) e usa `charge.transfer` (ID do Transfer, existe só em destination charges) — grava em `pagamentos`: `stripe_transfer_id`, `stripe_taxa_valor`, `comissao_valor`, `valor_liquido_loja`.

**Repasse automático via `payout.paid`:** é evento de **conta conectada** (da loja), não da plataforma — exige um **endpoint de webhook SEPARADO no dashboard Stripe**, criado com escopo "Contas conectadas" (não "Sua conta"), com segredo de assinatura DIFERENTE do endpoint normal. **Telas:** `StripeRepassePanel.jsx` novo em `/restaurante/financeiro` (não mostra tarifa Stripe — não afeta a loja). Aba "Stripe" nova em `/admin/comissoes` (mostra tarifa + margem líquida). - `orders.frete_cobrado`/`frete_excedente_cobrado` continuam gravados com os valores REAIS (base+excedente) mesmo quando não entram no total do cliente — servem de repasse ao motoboy (`ComissaoService.registrarComissaoEntrega`, inalterado) e alimentam o card de "ganho estimado" no app do motoboy (`motoboy.service.ts pedidosDisponiveisTodos`/`pedidosDisponiveis`, `ganho_estimado = frete_cobrado + frete_excedente_cobrado`, sem somar o "adicional" de `motoboy_comissao_tipo` — decisão explícita do usuário pra manter o preview simples).

## Incidente real corrigido (2026-09-26): 2FA por e-mail quebrado em produção — RESEND_API_KEY presa a domínio errado

Descoberto testando o login admin pra validar a feature de páginas legais acima: `admin@delivery.com` (local) tinha `two_factor_method='email'` e o login travava em "Não foi possível enviar o código de verificação agora" (`auth-login.service.ts`, mensagem genérica de propósito — engole qualquer falha de `TwoFactorEmailService.enviarCodigo`). Usuário confirmou que **o mesmo erro acontecia em produção** — ou seja, todo admin/dono de restaurante com 2FA por e-mail ativo estava impedido de logar de verdade, não só localmente.

**Causa raiz encontrada testando direto contra a API do Resend** (`curl POST https://api.resend.com/emails` com a `RESEND_API_KEY` do `.env`): `400 "The associated domain with your API key is not verified. Please, create a new API key with full access or with a verified domain."` — mesmo com o domínio `pediuvai.com.br` **verificado de verdade** no painel do Resend (usuário confirmou, verificado desde 02/09) e mesmo trocando o remetente pro exato `suporte@pediuvai.com.br` configurado lá. A chave antiga (`re_AEeT9f2x...`) ficou presa a um domínio diferente do que existia (ou não existia) no momento em que ela foi criada — API key restrita do Resend não "adota" um domínio verificado depois, precisa ser recriada.

**Corrigido:** usuário gerou uma API key nova no painel do Resend e trocou em produção (confirmou funcionando por lá). ## Bug real: 500 "Internal server error" ao atribuir plano "Grátis" em /admin/empresas (2026-10-09)

Usuário reportou: admin troca o plano de uma empresa em produção, escolhe o plano "Grátis", recebe `Internal server error` num alert e a troca não persiste.

O INSERT/UPDATE falha, não tem catch específico, e o NestJS devolve o 500 genérico — e como a escrita falhou, nada persiste (mesmo bug, não dois problemas).

**Como foi diagnosticado** (sem acesso a logs de produção): `npx supabase db query --linked "select ... from planos"` (leitura direta, read-only) achou o `trial_dias` suspeito; reproduzido localmente criando um plano idêntico e chamando `PUT /planos/assinaturas/:id` direto via curl (sessão de admin obtida trocando a senha do usuário admin local via Supabase Admin API, só em dev) — bateu 500 idêntico. `supabase db query --linked` também serve pra **escrever** (`UPDATE ... RETURNING`), usado pra corrigir o dado direto (não precisou de migration, é dado, não schema).

**Fix aplicado:**
1. Dado em produção corrigido direto (`UPDATE planos SET trial_dias = 0 WHERE id = 17`) — plano já tem `valor=0`, não precisa de trial nenhum.
2. `CriarPlanoDto`/`AtualizarPlanoDto` (`server_delivery/src/planos/dto/`) ganharam `@Max(3650)` em `trial_dias` — qualquer tentativa futura de repetir a gambiarra agora recebe 400 limpo ("trial_dias must not be greater than 3650"), não mais 500.
3. **Achado colateral importante**: o backend local (porta 3002) estava rodando `node dist/src/main` (build compilado), **não** em watch mode — editar `.ts` não tinha efeito nenhum até eu descobrir isso (via `wmic process ... get CommandLine`), rodar `npm run build` e reiniciar o processo manualmente. Qualquer teste "ao vivo" contra o backend local precisa checar isso primeiro (`netstat` + `wmic process where "ProcessId=X" get CommandLine`), senão o teste valida código desatualizado.

**Why:** registra que "grátis pra sempre" só deve ser implementado via `cortesia_ate` (timestamp realista, ~50 anos), nunca via `trial_dias` grande — datas muito distantes no futuro (>9999 ano) quebram o formato ISO8601/timestamp em várias camadas (JS Date extended format → Postgres). Também registra que `supabase db query --linked` é a ferramenta certa pra diagnosticar/corrigir dado de produção sem precisar de acesso a logs do EasyPanel.
**How to apply:** qualquer campo "dias"/"prazo" que vire `hoje + N dias` numa feature nova deve ter um `@Max` razoável no DTO (anos, não milênios). Se um bug em produção não reproduz "no ar" pela leitura do código, usar `supabase db query --linked` (read-only primeiro, sempre) pra olhar os dados reais antes de ficar só especulando por código estático. Antes de testar qualquer coisa "ao vivo" contra `localhost:3002`, confirmar que o processo não é um `dist/` parado num build antigo.

## Upload de imagem de produto migrado pro Cloudflare R2 (2026-10-13) — em produção

Motivação: pediuvai.com.br (nome comercial do DeliveryHub) é UGC pesado em foto/vídeo de produto; Supabase Storage cobra egress ($0,09/GB sem cache, $0,03/GB com cache do próprio Supabase, 250GB inclusos no Pro) — R2 tem egress **zero** sempre e storage mais barato ($0,015/GB vs $0,0213/GB). Decisão: não trocar banco de dados nem seguir sugestão solta de usar MongoDB (violaria [[feedback_monolito_modular_padrao]] e nem resolve nada — Mongo não é object storage). Caminho escolhido foi **híbrido direto**: backend NestJS fala com R2 via SDK S3 próprio, sem passar pelo Supabase Storage nem pelo self-hosted Supabase que o usuário instalou na VPS Hostinger nesse meio-tempo (esse self-hosted ficou só explorado — tela de "Wrappers/FDW" do Supabase Studio self-hosted não tem nada a ver com object storage, é só confusão de nome com `cfd1_wrapper`, que conecta no Cloudflare **D1**, banco relacional, não no R2).

**Implementado:** módulo novo `src/r2/` (`R2Module` global + `R2Service`, mesmo padrão do `SupabaseService`) nos dois checkouts de backend — `enviarArquivo`, `gerarUrlUploadAssinada`, `gerarUrlDownloadAssinada`, `montarUrlPublica`. Ligado no endpoint genérico `POST /restaurante/storage/upload?folder=` (`RestauranteService.uploadImage`, usado por produto/logo/banner/cardápio impresso) — trocou o bucket Supabase `restaurante-imagens` pelo bucket R2 `pediuvai-media`, contrato pro frontend (`{url}`) não mudou. Testado: `tsc --noEmit` + boot real (`node dist/src/main.js`, log `Nest application successfully started`) nos dois checkouts, teste de conexão real (PutObject + fetch da URL pública, HTTP 200), teste pelo app real, e confirmado funcionando em produção (EasyPanel) depois do deploy manual. Commits: `79a8ae2` (`serer_delivery`, mesmo hash no submódulo via `git reset --hard origin/main` após confirmar diff vazio — [[project_deliveryhub]] já documentava esse padrão) + `1f07777` (ponteiro do submódulo no frontend).

URL pública inicialmente usou a **Public Development URL** do R2 (`pub-<hash>.r2.dev`) só pra validar a conexão — substituída no mesmo dia pelo domínio custom definitivo, ver seção abaixo.

### Domínio custom do R2 configurado: `imag.pediuvai.com.br` (2026-10-13, mesmo dia) — confirmado em produção e local

Como a mídia já estava no R2 (não no Supabase Storage), o plano antigo de "domínio custom do Supabase por $10/mês" (discutido mais cedo nessa mesma sessão, antes do pivô pro R2) **não se aplicou** — R2 tem Custom Domain nativo e grátis, já que `pediuvai.com.br` é zona Cloudflare.

**Gotcha real: primeira tentativa foi conectar o domínio raiz `pediuvai.com.br`** (não um subdomínio) como Custom Domain do bucket. O painel do R2 mostrou "Active" normalmente, mas testar um objeto real (`curl https://pediuvai.com.br/_teste-conexao/...txt`) devolvia o `index.html` do app, não o arquivo — **o domínio raiz já tinha DNS apontado pro app principal (EasyPanel), e esse ganhou a disputa de rota; o Custom Domain do R2 ficou conectado mas inerte, sem erro visível nem no painel nem pro usuário final.** App em produção não quebrou (sorte de o app já estar servindo aquele hostname antes), mas também não adiantou nada configurar. Corrigido criando um **subdomínio dedicado** (`imag.pediuvai.com.br`, escolhido no lugar do `cdn.pediuvai.com.br` sugerido) — sem conflito, porque nenhum outro serviço usava esse hostname ainda. Não foi necessário remover a conexão do domínio raiz (R2 aceita múltiplos Custom Domains por bucket; o antigo só ficou parado, inofensivo).

**Segundo gotcha, no mesmo processo:** logo depois de conectar `imag.pediuvai.com.br`, testar devolvia `403` com `error code: 1014` ("CNAME Cross-User Banned") — não era erro de configuração, o painel mostrava status **"Inicializando"** (certificado TLS ainda sendo provisionado). Esperar ~1-2 minutos e testar de novo resolveu (`200`, conteúdo correto).

Validado via teste real nos dois lados: produção (upload pelo app, objeto apareceu em `pediuvai-media/produtos/` no painel R2) e local. `R2_PUBLIC_BASE_URL` atualizado nos dois `.env` (local) e nas env vars do EasyPanel (produção) de `pub-<hash>.r2.dev` pra `https://imag.pediuvai.com.br`.

**Why:** registra que Custom Domain "Active" no painel R2 não garante que o roteamento realmente funciona — precisa testar um objeto real, não só confiar no status. E que `error code: 1014` logo após conectar um domínio novo costuma ser só TLS ainda inicializando, não motivo pra desconfiar da configuração.
**How to apply:** ao conectar Custom Domain de bucket R2 em qualquer projeto, sempre usar subdomínio dedicado (nunca o domínio raiz/apex se ele já serve outra coisa), e sempre confirmar com um `curl` num objeto real do bucket antes de considerar pronto — status "Active" sozinho não é prova suficiente. Ver também [[feedback_cloudflare_r2_credenciais]] (mesmo tema, gotchas de setup do R2).

**Gotcha real, aconteceu 3x segidas ao gerar credencial R2:** a tela de criação de token da Cloudflare mostra **três valores diferentes** na confirmação (só aparece uma vez): **Token value** (prefixo `cfat_`/`cfut_`, é o token genérico Bearer da API REST da Cloudflare), **Access Key ID** (32 hex, sem prefixo) e **Secret Access Key** (64 hex, sem prefixo) — só os dois últimos servem de credencial S3-compatible. Usuário pegou o campo errado (Token value) duas vezes seguidas, e também confundiu a tela de "Account API Tokens" (genérica, template "Read all" por padrão, inclusive `Workers R2 Storage Read` **sem** Write — causa do primeiro `AccessDenied`) com a tela específica "R2 → Manage R2 API Tokens" (a única que gera o par Access Key ID/Secret Access Key certo, com opção de permissão "Object Read & Write" escopada por bucket).

**Gotcha adicional:** `.env` ganhou a chave `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` duplicada (valor antigo + novo) durante os ajustes manuais — em dotenv, **a última declaração da mesma chave no arquivo vence**, então o app continuaria lendo a credencial velha (que falhava) mesmo com a nova colada acima. `R2_PUBLIC_BASE_URL` também se perdeu numa edição manual no meio do processo.

**Why:** registra a arquitetura de mídia escolhida (R2 direto, não self-hosted Supabase Storage, não Mongo) pra não reabrir essa discussão do zero numa sessão futura, e documenta o fluxo de credencial do R2 porque já custou 3 rodadas de erro nessa sessão — provável de se repetir em outro projeto que também adote R2 (ver [[feedback_cloudflare_r2_credenciais]]).
**How to apply:** qualquer novo fluxo de upload de mídia nesse projeto (vídeo de produto, por exemplo) deve usar `R2Service` (injeção padrão, já é `@Global()`) em vez de reabrir Supabase Storage. Se aparecer `AccessDenied` numa chamada R2, suspeitar primeiro de token com permissão Read-only ou criado na tela errada da Cloudflare. Se aparecer comportamento "a env var certa está no arquivo mas não funciona", checar chave duplicada no `.env` antes de desconfiar do código.

### Todos os pontos de upload de imagem/vídeo migrados pro R2 (2026-10-13, mesmo dia) — em produção

Usuário notou que a aparência do admin (marketplace) continuava salvando no Supabase Storage — pediu consistência total. Varredura em todo o `src` (`grep .storage.from(`) achou 4 pontos restantes além do upload de produto já migrado:

- **`plataforma.service.ts`** (`uploadImagem`, aparência do marketplace/admin) — bucket `restaurante-imagens` (Supabase).
- **`academia.service.ts`** (`uploadVideo`, vídeos de treinamento) — bucket `academia-videos`, até 200MB.
- **`perfil.service.ts`** (`uploadFoto`, avatar do cliente) — bucket `customer-avatars`.
- **`motoboy.service.ts`** `uploadImagemRepasse` (comprovante Pix/nota fiscal de repasse) — bucket `comprovantes-pix`.

Esses 4 migrados direto (mesmo padrão do upload de produto) porque o banco sempre guardou a **URL completa**, não um path relativo — zero risco pro que já existe, só novo upload passa a ir pro R2.

**Quinto ponto, tratado separado por ser mais arriscado:** documentos de motoboy (CNH/CRLV/foto de veículo/comprovante de endereço/foto de perfil, bucket privado `motoboy-documentos` + `createSignedUrl`). Esse guarda só o **path relativo** no banco (`motoboys.documento_frente_url` etc.), não a URL — trocar o código sem mais cuidado quebraria o acesso de todo motoboy já cadastrado. Perguntado ao usuário, que escolheu migrar os arquivos primeiro:

1. Script (`@supabase/supabase-js` + `@aws-sdk/client-s3`) listou recursivamente o bucket Supabase de produção e copiou **22 arquivos** (nenhum erro) pro R2, **preservando a mesma chave exata** (`${motoboyId}/${campo}-${timestamp}.${ext}`, sem prefixo novo) — não apagou nada do Supabase, operação só de leitura lá.
2. Só depois trocou `upload-documento-motoboy.util.ts` (agora recebe `R2Service` em vez de `SupabaseService`) e `MotoboyService.signedUrl()` (agora `r2.gerarUrlDownloadAssinada()`) pra gravar/ler do R2.
3. Validado com teste real: URL assinada gerada pro R2 pra um dos arquivos migrados, `fetch` retornou `200` com `content-length` idêntico ao log da cópia.

**Gotcha de processo, não de código:** pra rodar o script de migração, a credencial de produção do Supabase precisou ir pro `.env` local — usuário inicialmente **sobrescreveu `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`** (as variáveis que o app inteiro usa) com os valores de produção, o que faria o backend local inteiro (não só a migração) passar a ler/gravar em produção real no próximo restart. Corrigido usando nomes isolados (`SUPABASE_PROD_URL`/`SUPABASE_PROD_SERVICE_ROLE_KEY`, só lidos pelo script pontual) e as linhas originais locais, que tinham ficado **comentadas** (`#SUPABASE_URL=...`) em vez de restauradas, precisaram ser descomentadas — sem isso o app ficaria sem `SUPABASE_URL` nenhuma.

Também apareceram no `.env`, sem uso em nenhum código, duas linhas de outro recurso da Cloudflare (`URI_DO_CATALOGO`/`NOME_DEPOSITO` — R2 Data Catalog/Iceberg, feature de data lake, não object storage) — removidas a pedido do usuário.

Commits: `3477961`/`ca052cc` (mesmo conteúdo, `serer_delivery`/submódulo) + `34bdeb2` (ponteiro). Validado `tsc --noEmit` + boot real (porta alternativa via `PORT=`, já que o processo de dev do usuário ocupava a 3002) nos dois checkouts.

**Why:** diferenciar "banco guarda URL completa" (migração seguro, zero coordenação) de "banco guarda path relativo + signed URL" (migração exige copiar o arquivo físico antes, senão quebra acesso de dado real já existente) é o critério que decide se dá pra trocar storage sem dor.
**How to apply:** antes de migrar qualquer storage novo nesse projeto (ou em qualquer outro com Supabase Storage + signed URLs), checar primeiro **o que está salvo no banco** — URL absoluta (`toPublicUrl`/`getPublicUrl` já embutido) é seguro trocar o backend livremente; path relativo consumido por `createSignedUrl()`/equivalente exige migração física dos arquivos existentes antes de trocar o código de leitura. Nunca sobrescrever `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` principais pra rodar um script pontual contra produção — sempre usar variáveis com nome isolado.
